日期：2026-09-10。版本：设计草案 v0.2。

状态：本文件保留容量选择和实验设计的依据，**不是正式启动授权**。用户随后授权了本地协议、代码和测试；当前实现规范见同目录 `EXPERIMENT_PROTOCOL.md` v0.9，本地验收状态见 `LOCAL_VALIDATION.md`。尚未做GPU smoke，未启动正式实验，也未授权新增U重跑或训练。原U/O/OC/R和OC3/OC5协议、结果保持不动。

修订记录：v0.2按用户澄清，将唯一主要问题改为“UK48是否优于U”，将UN48明确为扩容/额外非关键帧信息的辅助对照。48帧容量、两个新增组的选帧规则、权重、任务/seed建议均未改变；没有因此新增运行授权。

## 1. 本次要回答的问题

原先OC没有观察到提升，但OC是在固定32帧预算下优先放入边界帧、再做时间覆盖补全，并不保证保留原U的全部采样帧。因此，一个待检验的可能解释是：边界补充的潜在收益被原有均匀历史信息的损失抵消了。既有结果没有证明这一解释。

本次的**主要问题**是：

> 完整保留原版U的均匀历史、不挤掉已有帧，再扩容加入已观测的keyframe，能否比原U取得更好的完整任务表现？

**UN48是辅助对照，不取代上述主问题。** 它用于检查：若UK48比U更好，这种提升是否也会出现在补充等量随机非keyframe时，从而帮助区分边界信息的特殊价值与一般额外信息/扩容的共同影响。

| 比较 | 地位 | 回答的问题 |
|---|---|---|
| UK48 − U | 唯一主要比较 | 保留U后直接添加keyframe的整体方案有没有效果？ |
| UN48 − U | 辅助比较 | 保留U后添加随机非keyframe，是否也有收益？ |
| UK48 − UN48 | 辅助归因比较 | 两种扩容方案之间，关键帧补充是否有额外优势？ |

主比较检验的是“扩容并补充边界信息”这一整体干预，不是声称在容量不变条件下隔离了纯粹的边界语义效应。UN48同时添加了真实非边界内容，不是只有空槽位的纯容量对照，不能认为加入它就已经完全排除所有容量和位置编码因素。仅UK48优于UN48、但不优于U，不算主要问题的正面结果。

即使UK48有效，也不能单凭本实验就断言旧OC失败一定由均匀覆盖被挤占造成，或者边界就是全局最优关键帧。

keyframe沿用既有实验定义：实时观测到的 `current_task_index` 变化，首帧也标为边界。不是人工标注、不是示范H5的固定时间点，不使用未来阶段或最终成败。

## 2. 容量决定：固定48帧槽位，768个memory token槽位

原U基底仍是最多32帧；扩张后的物理容量固定为48帧。每帧16个tokens，因此每次输入的记忆张量有768个token槽位。有效帧多少由当前可见历史决定，剩余位置使用原有右侧padding和false mask。

选择依据来自已有轨迹，不是GPU性能或成功率预测：

| 已有数据上的容量核算 | 结果 |
|---|---:|
| U轨迹 | 800条 |
| U策略调用 | 14,599次 |
| U帧与可见边界帧去重合并后的最大数量 | 46帧 |
| U调用层面的99%分位 | 44帧 |
| 40帧容量会溢出的U轨迹 | 118条 |
| 40帧容量会溢出的U调用 | 1,153次 |
| U、OC、OC3、OC5全部历史的核算调用数 | 62,492次 |
| 上述全部历史中，按U32规则与边界合并的最大数量 | 46帧 |
| 上述历史中可见边界最大数 / 不在U中的新增边界最大数 | 15 / 14 |

48覆盖已观察到的最大需求并保留2帧余量，不必直接扩到64。记忆token槽位比原来增加50%，但**不能据此宣称总显存或总耗时增加50%**，实际开销要通过smoke测量。

统计没有按成功/失败筛选。因为旧正式结果已经被观察过，本次是明确标注的post-hoc后续实验，不能称为在完全未见test数据时制定的原始预注册研究。已有数据的最大值也不是新轨迹永不溢出的证明。

## 3. 两个新组

暂用独立标识 `UK48` 和 `UN48`，不得冒用或更改旧U、OC或R的定义。

| 项目 | UK48：U＋Keyframe | UN48：U＋随机非Keyframe |
|---|---|---|
| 基底 | 原U的最多32帧，完整保留 | 相同的原U32选择规则 |
| 新增内容 | 当前可见、且尚不在U中的全部边界帧 | 当前可见、既不在U也不是边界的随机帧 |
| 新增数量 | 当前历史中缺少的边界帧数 | 根据自身当前历史，计算相同定义的数量 |
| 扩容上限 | 48帧 / 768tokens | 48帧 / 768tokens |
| 剩余空位 | padding＋false mask | padding＋false mask |

不额外用Uniform或其他策略填满48个有效帧。否则将引入用户这次未提出的填充机制，无法直接解释为U＋key对U＋等量随机非key。

### 3.1 每次策略调用的精确定义

令 `H_t={0,...,t}` 为本组当前已经实际观测到的历史；`U_t` 为原始U32规则在这段历史上的输出；`B_t` 为当前可见的因果边界索引。

```text
new_keys = B_t - U_t
nonkey_candidates = H_t - (U_t union B_t)
m = len(new_keys)

UK48 = chronological_sort(U_t union new_keys)
UN48 = chronological_sort(U_t union sample_without_replacement(nonkey_candidates, m))
```

运行时基底必须调用原版 `get_frame_sampling_indices(t, 512, 16)`，而不是将768传给它。后者会把基底改成Uniform48，违反“在原U基础上追加”的定义。最终取特征与padding才使用新768预算。

对同一段历史，两个选择函数必须保留完全相同的U索引，并严格增加相同数量的不同帧。所有结果去重、按原历史时间排序；不能复制已有关键帧来增加权重，也不能重编号它们的原始历史时间。

例如：U已有32帧，已观测10个边界，其中3个在U中，则UK48只新增7帧；随机对照也新增7帧。两组各有39个有效帧、9个masked槽位，而不是各新增10帧。

### 3.2 “等量”与闭环因果性

两条独立闭环轨迹会逐渐产生不同历史，边界数量、终止时刻也可能不同。因此，“等量”严格指**同一当前历史下两套规则的新增数量相同**，不是保证不同轨迹在每个模型调用编号上都有完全相同的有效帧数量。

UN48只根据自身已经观测到的历史计算m。禁止用UK48另一条轨迹后续才出现的边界数、旧示范的完整长度、或终局阶段数给UN48安排容量。也不允许为了凑同样数量而暂停一组、延长轨迹或读取另一组未来状态。

随机对照仍用边界标签决定新增数量与排除候选，因此它准确的描述是“Oracle边界数量匹配的随机非边界对照”，不是完全不使用Oracle信息的旧RandomSamp。有效帧数本身可能携带进度信息；两套同历史规则共享这种数量信号。

### 3.3 早期历史、溢出与候选不足

- 历史不足32帧时，U已经包含全部历史，新增数量自然为0；按固定48容量padding。
- 新增帧不在U中，随机新增帧也不能是边界。U本来含有的边界帧不得从随机组删除。
- 若 `len(U_t union B_t)>48`，或者非边界候选数不足m，保存当前证据并作为**协议边界事件硬停**。不能默默删关键帧、补重复帧、借未来帧或减少随机组数量。
- 硬停不是普通机器人任务失败，不可计为成功率中的fail，也不能静默排除该episode。继续正式研究需要记录事件、修订规则并重新验证；在此之前不得宣称矩阵完成。
- 现有62,492次调用中没有上述容量或非key候选不足事件，但新组仍必须检查。

随机选择使用独立、确定性的RNG，不影响原动作采样随机流。正式版应预先冻结包含实验family、split、task、episode和policy-call编号的seed命名空间；开发smoke与正式test不能共用随机选帧seed。原环境映射和动作策略seed7不变，不根据结果挑随机种子。

## 4. 保持不变的部分及实验范围

建议继续使用原16个任务、test episode 0–49、相同环境seed映射与难度，两个新组共1,600条完整闭环轨迹。正式任务矩阵和随机seed清单在启动协议中生成、校验并冻结。

沿用 released `perceptual-framesamp-modul` 的79999 checkpoint，不训练、不改权重；历史front-view输入、当前front/wrist、task instruction、每帧16tokens、Modulator、20步动作提案、执行16步后重规划及1300步上限保持不变。不得另加symbolic subgoal、邻域帧、动作Oracle或分支挑赢家。

两个新组必须在同一固定软件/硬件执行方案下成对运行，每个任务/episode重新初始化并核验初始图像与状态。服务器选择将在启动前确定：先前建议回Athena是为修复旧OC3/OC5相对旧基线的输入配对，并不意味着这个自带新对照的实验也必须在Athena。

U是主要比较必需的基线，不能被降为仅作描述性参考。优先检查是否可以复用已有U：除本次明确要改变的记忆容量/新增内容外，必须核对初始输入与状态、环境seed、任务条件、checkpoint、执行代码与软件/硬件方案等可比性证据。不能因为seed相同就默认跨服务器的旧U已是严格匹配对照。

如果现有U无法满足可比性要求，正式主比较必须先解决这一阻碍；可提出在选定环境补跑U的独立方案，并取得用户批准。不得自行增加800条U轨迹，也不得把UK48−UN48改成主要比较来绕过缺失的U基线。基线来源未确定前，1,600条只是两个新增组的建议数量，不是保证完整研究最终只需这些运行。

此前授权的700条输入一致性复跑针对OC3/OC5，并不等于授权本实验的U基线重跑。本轮没有启动其中任何一项。

## 5. 代码审查发现：扩容并非仅改一个数字

### 5.1 模型参数形状具备扩容的可能性

现有特征编码和MemoryAttention参数主要依赖特征宽度，而非512这个记忆长度；输入形状由history budget生成。因此同checkpoint在768tokens下推理在结构上可行，但目前还没有用真实checkpoint完成新形状加载与GPU推理验证。

准备后的单样本字段预期为：image `[768,2048]`，position `[768,768]`，state占位字段 `[768,8]`，bool mask `[768]`；最终记忆 `[1,768,1024]`。state memory仍禁用，字段占位不代表启用了新的状态输入。

### 5.2 必须独立适配的接口

- checkpoint loader会用checkpoint旁的 `history_config.txt` 覆盖请求配置。必须新增明确、可追溯的推理预算覆盖方式，并打印实际生效配置；不能编辑原checkpoint文件或原512配置。
- 旧实验的selector、mask、artifact与聚合校验中有32/512硬约束。新family应有独立的48/768验证契约，不得为了新实验放宽旧研究的验证条件。
- 基底U固定使用旧32规则；扩容只作用于最终输入预算。
- 模型权重必须严格加载，没有新增、缺失或随机初始化的训练参数；记录原权重身份与生效配置。

### 5.3 必须披露的位置编码变化

`MemoryAttention` 使用完整memory长度构造action-query的RoPE位置：query位置从 `mem_len` 开始，memory-key位置从0开始。因此即便只是把同样的U32帧放进更大的张量，并把新增槽位mask掉，512→768也可能改变模型输出。

这意味着：

1. UK48与UN48都用768槽位，辅助归因对照共享扩容及其位置编码设置。
2. UK48对U32的差异仍然是本研究的主要比较，但它度量扩容补充方案的整体效果，不能全部归因为“新增关键帧的信息”；位置分布随扩容改变也可能影响结果。跨环境差异则是需要另外控制的混杂，不能当作授权干预的一部分。
3. 不偷偷更改RoPE来强行恢复旧U输出，那将是另一个模型结构干预。
4. 在smoke里加入“同样U帧、512槽vs768槽”的固定输入诊断，记录动作差异，而不是预设补padding一定无影响。该诊断不算新增第三个正式实验组。

## 6. 实现后的验收门槛

CPU与fixture：原U32索引完整保留；只增加差集key；随机候选排除U与全部边界；同历史等量；唯一且严格因果的索引；早期padding；溢出/不足硬停；独立seed复现；每帧16tokens及768固定形状；旧研究32/512行为回归保持。

GPU smoke须使用开发数据：真实checkpoint严格加载；同扩容形状、同有效索引、同输入及同噪声的重复推理检查；上述padding位置诊断；短/长历史推理；重置清空memory与RNG；有限输出；20×8动作输出；峰值显存与推理延迟。不能用正式成功率来挑选48或64，也不能看smoke胜负后改选择器。

正式每次调用应保存：base U索引、可见boundary、新增key候选、非key候选数、新增数量、最终索引、有效/填充帧与token数量、mask与张量摘要、随机seed、绝对历史索引、容量与生效配置，以及既有完整provenance。

唯一主要比较为UK48与U的完整任务成功率差，保持任务/episode配对。UN48−U和UK48−UN48作为两个辅助比较。沿用既有层次bootstrap与配对检验框架；正式版需在运行前冻结U基线来源、统计seed与重复数、辅助检验多重比较处理及“提升”的判据。不得只看点估计或单次p值就宣称机制成立。逐任务与记忆数量诊断为探索性，不用它们事后改排除规则。

结果解释按以下顺序进行，所有“更好”都需结合效应大小及不确定性，而非只比较几个百分比：

- UK48优于U，且UK48优于UN48：支持直接添加keyframe的整体方案有效，并支持其相对于该随机非key对照的额外价值；不是完全排除所有扩容机制的证明。
- UK48和UN48都优于U，但UK48−UN48区间仍覆盖有意义的正负差异：方案可能有效，但关键帧特异优势尚不能确定。不能把“未显著不同”写成“效果相等”或“提升全由容量造成”。
- UK48优于UN48、但没有证据优于U：只说明该随机补充可能更差，不算验证了用户的主要假设。
- UK48没有显示优于U：结合区间判断是证据不足，还是能排除预先定义的实用提升；不能据此否定所有记忆设计或所有匹配训练方案。

本草案随后细化为同目录 `EXPERIMENT_PROTOCOL.md` v0.9，并进入用户授权的本地实现与CPU验证阶段。GPU smoke及正式运行仍分别需要明确启动授权；已有本地接口不等于远端完整运行器已就绪。
